## 1페이지 — 표지

안녕하세요. 연산 자원 공유 시스템 M.A.R.S를 개발하고 있는 G조입니다.

M.A.R.S는 여러 기기의 CPU와 GPU 같은 연산 자원을 Worker로 연결하고, 여러 AI 에이전트로 구성된 워크플로우의 업무를 각 Worker에 나누어 실행하는 시스템입니다.

이번 발표에서는 전체 일정과 현재까지 구현한 주요 기능, 개발 과정에서 해결한 핵심 문제, 그리고 앞으로 개선할 내용을 순서대로 말씀드리겠습니다.

## 4페이지 — 개발 일정(WBS)

WBS에서는 요구사항을 회원 관리, 기기 관리, 서비스와 워크플로우 관리, 실행 관리 등의 기능 단위로 나누어 진행 상황을 추적했습니다.

파란색은 구현, 초록색은 완료 또는 해결된 항목이며, 주황색과 빨간색은 부분 구현이나 이슈가 있었던 항목, 보라색은 추가 수정이 예정된 항목입니다.

현재 회원가입과 로그인, Worker 등록 및 상태 확인, 워크플로우 생성·수정·실행, 작업 결과 조회 같은 핵심 흐름은 대부분 구현된 상태입니다.

개발 중 추가로 필요하다고 판단한 기능도 WBS에 반영했습니다. 예를 들어 업로드 파일 보관과 에이전트 연결, 공유 디렉터리 관리, Worker별 디렉터리 바인딩, CPU·GPU 자원 한도 기반 배정, 실행 결과 조회 및 다운로드 기능이 있습니다.

즉, 초기 요구사항 구현에서 끝내지 않고 실제 통합 과정에서 발견한 운영상의 요구까지 일정에 추가하여 보완하고 있습니다.

> 다음 페이지: “이제 실제 구현 화면을 중심으로 설명드리겠습니다.”

## 5페이지 — 주요 구현 현황: 워크플로우 생성

이 화면은 새로운 멀티 에이전트 워크플로우를 만드는 시작 화면입니다.

사용자가 수행하려는 업무를 자연어로 입력하면, 서버가 로컬 Ollama 모델에 생성 요청을 보내 필요한 에이전트의 역할과 실행 순서를 그래프 형태로 구성합니다.

예를 들어 자료 조사, 내용 분석, 결과 정리처럼 하나의 요청을 여러 단계로 분리하고, 각 단계가 어떤 결과를 다음 단계에 전달할지 자동으로 설계합니다. 생성 결과가 유효한 DAG인지 서버에서 검증하며, LLM 응답이 잘못된 JSON이거나 순환 구조인 경우에는 재시도와 안전한 기본 워크플로우 생성을 통해 실패를 방지합니다.

현재 실행의 핵심은 Worker에 설치된 로컬 Ollama 모델이며, 화면의 클라우드 모델 영역은 향후 외부 LLM을 함께 선택할 수 있도록 확장하려는 방향을 나타냅니다.

> 다음 페이지: “생성된 워크플로우는 다음과 같이 직접 확인하고 수정할 수 있습니다.”

## 6페이지 — 주요 구현 현황: 워크플로우 편집

이 화면은 생성된 워크플로우를 시각적으로 편집하는 빌더입니다.

예시에서는 제주도 여행 일정이라는 요청을 관광지도 PDF 조사, 여행 계획 작성, 최종 결과 정리의 세 단계로 구성했습니다. 각 블록은 하나의 Agent 작업이며, 연결선은 선행 작업의 결과가 다음 작업의 입력으로 전달된다는 의미입니다.

각 Agent에는 역할 프롬프트와 사용할 모델을 설정할 수 있고, 특정 Worker를 직접 지정하거나 자동 배정을 선택할 수 있습니다. 파일이나 공유 디렉터리도 Agent 단위로 연결할 수 있어, 필요한 자료에만 접근하도록 범위를 제한했습니다.

자동 배정은 중앙 서버가 모든 장비의 점수를 계산하는 방식이 아니라, 조건을 만족하는 Worker가 작업을 먼저 요청해 원자적으로 선점하는 방식입니다. 이때 사용자 소유 관계, 디렉터리 연결 여부, CPU·GPU 사용 한도를 검사합니다.

> 다음 페이지: “구성이 끝나면 실제 실행 요청을 입력합니다.”

## 7페이지 — 주요 구현 현황: 실행과 진행 상태

왼쪽은 워크플로우 실행 전 화면입니다. 같은 워크플로우를 반복해서 사용할 수 있도록 구조와 역할은 저장하고, 실행할 때마다 이번 작업에 필요한 구체적인 요청을 별도로 입력합니다.

실행을 시작하면 각 Agent가 TaskRecord로 생성됩니다. 선행 작업이 없는 Agent는 ready 상태가 되고, 앞 단계의 결과가 필요한 Agent는 blocked 상태에서 기다립니다.

오른쪽 화면에서는 전체 진행률과 각 Agent의 상태, 실제 배정된 Worker를 확인할 수 있습니다. 선행 Agent가 완료되면 그 출력이 다음 Agent의 입력 컨텍스트에 포함되고, 필요한 조건이 충족된 후 다음 작업이 ready 상태로 전환됩니다.

사용자는 실행 도중 전체 작업을 취소할 수도 있으며, 취소된 미완료 작업은 정리하고 이미 완료된 결과는 보존하도록 구현했습니다.

> 다음 페이지: “모든 Agent가 완료되면 결과를 한 화면에서 확인할 수 있습니다.”

---

## 8페이지 — 주요 구현 현황: 실행 결과

이 화면은 워크플로우 실행이 완료된 결과 화면입니다.

상단에서는 전체 완료 여부와 진행률을 확인할 수 있고, 실행 타임라인에서는 각 Agent가 어떤 Worker에서 언제 완료됐는지를 확인할 수 있습니다.

모든 작업이 끝나면 말단 Agent들의 결과를 모아 최종 출력으로 구성합니다. 사용자는 결과를 화면에서 확인하거나 보고서 형태로 내려받을 수 있으며, 왼쪽 실행 이력에서 이전 실행의 성공과 실패 상태도 다시 확인할 수 있습니다.

예시에서는 첫 번째 Agent가 지도 PDF를 분석하고, 두 번째 Agent가 여행 계획을 작성한 뒤, 마지막 Agent가 내용을 정리해 최종 일정으로 출력했습니다. 이를 통해 단일 LLM 호출이 아니라 여러 Agent와 Worker가 순서에 따라 협업하는 전체 실행 흐름을 구현했습니다.

> 다음 페이지: “통합 과정에서 발견하고 해결한 주요 문제를 설명드리겠습니다.”

## 9페이지 — 주요 버그 수정 및 개선

첫 번째는 작업을 수행하던 Worker가 종료되면 작업이 계속 running 상태로 남아 전체 워크플로우가 끝나지 않는 문제였습니다.

이를 해결하기 위해 Worker의 하트비트가 일정 시간 이상 끊기면 해당 작업을 running에서 ready로 되돌리고, 기존 배정 정보를 해제해 다른 온라인 Worker가 이어서 가져갈 수 있도록 했습니다.

두 번째는 Worker를 재설치하거나 설정을 초기화한 뒤 같은 이름으로 재등록할 때 기존 기기 정보와 충돌하는 문제였습니다. 재등록 시 새로운 기기를 만들지 않고 기존 device_id를 유지하면서, 장비 사양을 갱신하고 통신용 API 키만 새로 발급하도록 변경했습니다. 따라서 기존 작업 배정과 디렉터리 연결도 유지됩니다.

세 번째는 디렉터리를 단순 경로 문자열로 관리해 소유 사용자와 연결된 Worker, Worker별 실제 저장 위치를 구분하기 어려웠던 문제입니다. 이를 SharedDirectory와 DirectoryMount 구조로 분리했습니다. 워크플로우에는 논리적인 directory_id를 저장하고, 실행 시 Worker별 실제 로컬 경로로 변환합니다. 실제 폴더의 접근 가능 여부와 파일 목록은 Worker에 디렉터리 검사 요청을 보내 확인할 수 있도록 구성했습니다.

추가로 여러 Worker가 동시에 같은 작업을 가져가지 못하도록 ready 상태에 대한 원자적 업데이트로 작업을 선점하도록 보완했습니다.

> 다음 페이지: “현재 구조에서 앞으로 개선할 부분은 다음과 같습니다.”

## 10페이지 — 개선 및 추가할 내용

첫 번째 과제는 자동 업무 배정 방식의 개선입니다.

현재 자동 모드는 조건을 만족하는 Worker 중 먼저 작업을 요청한 Worker가 배정받는 선착순 방식입니다. 기본적인 CPU·GPU 사용 한도와 디렉터리 연결 여부는 검사하지만, 장비의 실제 성능, 현재 작업 수, 모델 보유 여부, 예상 처리 시간까지 비교하지는 않습니다.

앞으로는 이런 정보를 점수화해 작업 특성에 더 적합한 Worker를 선택하는 스케줄링 방식을 검토할 계획입니다.

두 번째는 LLM 모델 확장입니다. 현재는 Ollama HTTP API를 이용해 오픈소스 모델을 검색·다운로드하고 로컬 Worker에서 실행합니다. 다만 소형 모델에서는 도구 사용 지시를 제대로 따르지 않거나 한국어와 영어가 섞이는 문제가 발생할 수 있습니다. 모델별 품질을 평가하고 프롬프트를 보정하거나, 기준에 미달하는 모델은 추천 대상에서 제외할 예정입니다. 또한 OpenAI API와 같은 외부 클라우드 LLM도 선택할 수 있도록 실행 구조를 확장할 계획입니다.

마지막으로 현재 사용자별로 격리된 Worker를 권한 기반으로 공유하고, 연산 자원의 제공량과 사용량을 크레딧으로 보상·정산하는 구조도 장기 확장 방향으로 검토하고 있습니다.

> 다음 페이지: “마지막으로 남은 기간의 활용 계획입니다.”

## 11페이지 — 남은 일정 활용 계획

9월에는 WBS에서 아직 부분 완성 상태인 기능을 마무리하고, Worker 기기 앱의 미완성 UI를 보완하겠습니다. 동시에 지금까지 구현한 기능을 통합 테스트하면서 발견되는 오류를 계속 수정할 예정입니다.

10월에는 전체 시나리오를 중심으로 테스트를 진행하고, 사용자 문서와 개발 문서를 작성하며, 최종 발표에서 보여줄 데모 흐름을 준비하겠습니다.

11월에는 문서를 최종 정리하고 실제 발표 데모를 반복 점검한 뒤, 핵심 구조와 결과를 한눈에 전달할 수 있는 포스터를 제작할 계획입니다.

남은 기간에는 새로운 기능을 무리하게 늘리기보다, 현재 구현된 워크플로우 생성부터 Worker 배정, 실행, 장애 복구, 결과 확인까지의 전체 흐름을 안정화하는 데 우선순위를 두겠습니다.

> 다음 페이지: “이상으로 발표를 마치겠습니다.”
