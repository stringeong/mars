# 로그 전처리 품질 회귀 시험 계획

## 1. 배경과 목적

멘토링에서 제안된 품질 회귀 시험을 전체 기능에 한꺼번에 적용하기보다, 결과를
명확히 참·거짓으로 판정할 수 있는 **로그 전처리**부터 검증한다.

이 시험의 목적은 모델, 프롬프트 또는 워크플로가 바뀐 뒤에도 로그의 경보 여부를
기존과 동일한 수준으로 판정하는지 확인하는 것이다. 또한 M.A.R.S.의
로컬·클라우드 혼합 처리와 클라우드 단독 처리의 정확도 및 클라우드 토큰 사용량을
비교한다.

## 2. 시험 범위

### 포함

- 로그 줄별 경보 여부 판정
- 정상 로그를 경보로 잘못 판정하는 오탐 확인
- 경보 로그를 놓치는 누락 확인
- 동일 입력을 반복 실행했을 때의 결과 일관성 확인
- M.A.R.S. 방식과 클라우드 단독 방식의 정확도·토큰 사용량 비교

### 제외

- 로그에 직접 나타나지 않은 원인 추론
- 사람이 결과의 유용성을 주관적으로 평가하는 5점 척도
- 실제 운영 로그 전체를 대표하는 성능 주장

이번 시험은 자연어 품질 평가가 아니라, 공개 데이터셋의 정답 라벨과 모델 결과를
비교하는 회귀 시험이다.

## 3. 선정 데이터셋: LogHub BGL 2K

1차 시험에는 LogHub의 Blue Gene/L(BGL) 2K 데이터셋을 사용한다.

- 원본 로그: <https://github.com/logpai/loghub-2.0/blob/main/2k_dataset/BGL/BGL_2k.log>
- 정답용 구조화 데이터: <https://github.com/logpai/loghub-2.0/blob/main/2k_dataset/BGL/BGL_2k.log_structured.csv>
- 데이터셋 설명: <https://github.com/logpai/loghub/blob/master/BGL/README.md>
- 사용 조건: <https://github.com/logpai/loghub-2.0/blob/main/LICENSE>

BGL은 각 로그 줄의 첫 번째 필드에 경보 라벨을 제공한다.

| 정답 라벨 | 의미 | 시험 정답 |
|---|---|---|
| `-` | 비경보 로그 | `false` |
| `-` 이외의 값 | 경보 로그 | `true` |

이 데이터셋은 메시지에 `error`라는 단어가 있어도 정답이 정상일 수 있다. 따라서
단순 키워드 검색이 아니라 로그 문맥을 바탕으로 경보 여부를 판정하는지 확인할 수 있다.

구조화 CSV에는 `Label`, `Time`, `Node`, `Component`, `Level`, `Content`,
`EventId`가 포함되어 있어, 이후 필드 추출 시험으로 범위를 확장할 수도 있다.

> 데이터셋은 연구·학술 목적 사용을 전제로 하며, 보고서와 배포물에는 LogHub 저장소와
> 관련 논문을 인용하고 데이터셋 라이선스 고지를 포함한다.

## 4. 입력과 기대 출력

모델에는 원본 로그만 제공한다. 구조화 CSV의 `Label`은 정답 채점에만 사용하며,
모델 입력에는 포함하지 않는다.

로그 100줄을 하나의 묶음으로 전달하고, 입력 순서를 유지한 불리언 배열을 반환하게
한다.

```json
{
  "predictions": [false, false, true, false]
}
```

- `true`: 운영상 경보 또는 이상을 나타내는 로그
- `false`: 정상 또는 비경보 로그

출력은 설명문 없이 유효한 JSON 하나여야 한다. 각 묶음의 예측값 수는 입력 로그 줄
수와 같아야 한다.

## 5. T/F 판정 방식

각 로그 줄에 대해 다음과 같이 판정한다.

```text
정답: Label != "-"
예측: 모델이 반환한 predictions[n]

정답과 예측이 같으면 T
정답과 예측이 다르면 F
```

| 구분 | 정답 | 예측 | 판정 | 의미 |
|---|---:|---:|---|---|
| True Positive | true | true | T | 경보를 올바르게 탐지 |
| True Negative | false | false | T | 정상 로그를 올바르게 판정 |
| False Positive | false | true | F | 정상 로그를 경보로 오탐 |
| False Negative | true | false | F | 경보 로그를 누락 |

출력이 JSON으로 파싱되지 않거나, 예측값 수가 입력 줄 수와 다르면 해당 묶음은 실패로
처리한다.

## 6. 시험 구성

BGL 2K 전체를 100줄 단위로 나누어 20개 묶음으로 시험한다. 각 묶음은 같은 조건에서
3회 실행하여 모델 출력의 변동성도 확인한다.

| 항목 | 값 |
|---|---:|
| 원본 로그 수 | 2,000줄 |
| 묶음 크기 | 100줄 |
| 시험 묶음 수 | 20개 |
| 방식 | M.A.R.S. 혼합 처리, 클라우드 단독 처리 |
| 반복 횟수 | 방식·묶음당 3회 |
| 총 모델 실행 | 120회 |

처음에는 M.A.R.S. 방식만 실행해 기준 결과를 만들고, 일정이 허용되면 같은 입력으로
클라우드 단독 처리를 추가한다.

## 7. 실행 절차

1. BGL 원본 로그와 구조화 CSV를 `benchmark/` 아래에 준비한다.
2. 원본 로그를 100줄 단위 입력 파일로 분할한다.
3. 각 입력 파일을 M.A.R.S. 워크플로에 전달한다.
4. 모델 출력 JSON을 입력 파일과 같은 이름으로 저장한다.
5. 구조화 CSV의 라벨과 모델 예측을 비교해 줄별 T/F를 계산한다.
6. 같은 입력을 3회 실행해 결과가 일관적인지 확인한다.
7. 수정 전 기준 결과와 비교해 새로 실패한 항목이 있는지 확인한다.
8. 실패 사례는 원인을 기록하고 수정 후 같은 입력으로 재시험한다.

구체적인 파일 분할·채점 도구 사용법은
[BGL 로그 회귀 시험 도구 사용법](bgl-log-regression-test.md)을 따른다.

## 8. 측정 지표와 합격 기준

### 측정 지표

- 정확도(Accuracy)
- 정밀도(Precision)
- 재현율(Recall)
- F1 점수
- 오탐 수(False Positive)
- 누락 수(False Negative)
- JSON 형식 준수율
- 반복 실행 간 판정 일치율
- 클라우드 단독 대비 클라우드 토큰 절감률

### 초기 합격 기준

| 항목 | 기준 |
|---|---:|
| 정확도 | 95% 이상 |
| JSON 형식 준수율 | 100% |
| 변경 전 기준 결과에서 새롭게 발생한 실패 | 0건 |
| 같은 입력 3회 실행 시 결과 불일치 | 0건 |
| 경보 누락 | 별도 확인 및 원인 기록 |

경보 누락은 운영상 위험이 크므로, 정확도가 기준을 통과하더라도 발생 사례를 반드시
별도로 검토한다. 초기 결과를 바탕으로 합격 기준을 확정하되, 특정 실패를 통과시키기
위해 시험 후 기준을 완화하지 않는다.

## 9. 결과 기록

채점 결과는 다음 두 파일로 남긴다.

- `summary.json`: 정확도, TP, TN, FP, FN, 정밀도, 재현율, F1
- `details.csv`: 원본 줄별 정답, 모델 예측, T/F 판정, 오류 내용

실패한 행에는 기대값, 실제 예측, 입력 묶음 번호, 실행 방식, 반복 번호, 추정 원인,
수정 여부를 함께 기록한다.

## 10. 보고서에 포함할 내용

- 로그 전처리를 첫 회귀 시험 대상으로 정한 이유
- BGL 데이터셋과 정답 라벨의 구성
- 모델 입력과 정답 데이터를 분리한 방법
- T/F 판정 규칙 및 평가 지표
- M.A.R.S. 방식의 정확도·오탐·누락·반복 일치율
- 클라우드 단독 방식과의 정확도 및 토큰 사용량 비교(수행 시)
- 대표 실패 사례와 수정 결과
- 합성·공개 데이터셋 중심 시험이라는 한계와 향후 실제 환경 로그 시험 계획
